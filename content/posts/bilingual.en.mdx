## Rules first

The site has two languages, English and Chinese. Before writing any code I set four rules, and everything else follows from them:

1. Every page lives under `/en` or `/zh`, so the language is part of the URL.
2. The root URL redirects by browser language, falling back to English.
3. Switching languages keeps you on the same page.
4. Posts don't have to be bilingual; translations link to each other.

With only two languages, an i18n library isn't needed. UI strings live in two dictionary files, and the Chinese dictionary takes its type from the English one: `type Dictionary = typeof en`. A missing Chinese string is a type error.

## Picking a language at the root

Next.js 16 renamed middleware to proxy; the file is `proxy.ts` at the project root. It only handles paths without a language prefix: `/en/…` and `/zh/…` pass through, and everything else redirects to the same path with a language in front, query string included.

> The redirect is a 307, not a 308. The target depends on the visitor, so browsers must not cache it as permanent.

### Order of checks

Cookie first, then the browser's languages, then the English default. The cookie is written when someone uses the language switcher, which is an explicit choice, so it wins. These are the cases I checked on the live site:

| Request | Redirects to | Why |
| --- | --- | --- |
| cookie `zh` + `en` | `/zh` | The cookie wins |
| `zh-CN,zh;q=0.9,en;q=0.8` | `/zh` | Primary subtag is zh |
| `fr,zh;q=0.5` | `/zh` | fr isn't supported, so the next one |
| `zh;q=0,en` | `/en` | q=0 means not acceptable |
| `de` | `/en` | Nothing supported, so the default |

### Parsing Accept-Language

Browsers send a list of weighted language tags. Sort by q from high to low, keep the original order on ties, and compare only the primary subtag, so zh-CN, zh-TW and zh-HK all count as zh:

```ts
// Picks the highest-q supported language, matching on the primary subtag
// so zh-CN, zh-TW and zh-HK all map to zh.
function matchAcceptLanguage(header: string | null): Locale | undefined {
  if (!header) return undefined;

  const ranked = header
    .split(",")
    .map((part, index) => {
      const [tag, ...params] = part.trim().split(";");
      const q = params.map((p) => p.trim()).find((p) => p.startsWith("q="));
      return {
        base: tag.trim().toLowerCase().split("-")[0],
        quality: q ? Number(q.slice(2)) : 1,
        index,
      };
    })
    .filter((entry) => entry.quality > 0)
    .sort((a, b) => b.quality - a.quality || a.index - b.index);

  for (const { base } of ranked) {
    if (hasLocale(base)) return base;
  }
  return undefined;
}
```

The `matcher` skips `_next/` and any path with a file extension, so the favicon and images are never redirected. The trade-off is that post slugs can't contain dots.

## Everything lives under `app/[lang]`

The language is the first URL segment and a parameter of the root layout: `app/[lang]/layout.tsx` is the root layout, so `<html lang>` follows the language. `generateStaticParams` returns `en` and `zh`, and both languages are built ahead of time.

Components don't pass `params` down. `next/root-params` provides `lang()`, so any server component can read the current language and load its dictionary.

The language switcher is the only part that runs in the browser. It swaps the first path segment for the other language and sets a cookie on click, so the next visit to the root remembers the choice.

## Posts don't have to be bilingual

Posts are MDX files in `content/posts/`, named `<slug>.<lang>.mdx`. Two files with the same slug and different languages are translations of each other, with no extra configuration.

When a translation exists, the end of the post links to it. When it doesn't, the other language's URL still works:

- In the post list, the post is labelled with its language.
- The post page shows the original with a one-line notice, such as “This post is only available in Chinese.”
- The canonical URL points to the original, so search engines don't treat the two URLs as duplicates.
